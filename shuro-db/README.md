# 全国 就労支援事業所データベース（shuro-db）

就労移行支援・就労継続支援A型/B型・就労定着支援の事業所を、全国横断で検索できるアプリです。
WAM NET の公的オープンデータを取り込み、正規化・名寄せしてローカルの SQLite に格納します。

**外部ライブラリへの依存はありません**（Node 22.5+ 同梱の `node:sqlite` と標準モジュールのみ）。
地図表示のみ、ブラウザ側で MapLibre GL JS を CDN から読み込みます。

---

## 使い方

```bash
cd shuro-db
npm run fetch         # WAM NET のオープンデータを取得（事業所の基本情報）
npm run fetch:extra   # 都道府県の工賃実績・生産活動の資料を取得
npm run build         # 正規化・名寄せしてDBを構築（data/shuro.db）
npm start             # http://localhost:8787
npm run export        # スプレッドシート用のCSVを data/export/ に書き出す
npm run audit         # 突合精度を実測する（事業所番号を正解データとして検証）
npm test              # 正規化・分類・突合ロジックのユニットテスト
```

`npm run fetch:all` で両方をまとめて取得できます（`fetch` は全期分）。

PDFで公表している都道府県があるため、工賃の取り込みには **`pdftotext`（poppler）** を使います。
無い場合はPDFのソースだけを飛ばして処理を続けます。

```bash
brew install poppler        # macOS
sudo apt install poppler-utils   # Debian / Ubuntu
```

- `npm run fetch` は最新期のみ取得します。`npm run fetch -- --all` で全期（2021年11月〜）、
  `npm run fetch -- 202509` で期を指定できます。複数期を入れると差分（新規・消失）が出ます。
- 取得済みのファイルは再ダウンロードしません。
- `npm run build` は毎回DBを作り直すため冪等です。

## データについて（重要）

### 出典

このアプリは3種類のデータを別々のソースから取り込み、突合しています。

| データ | 出典 | 粒度 | 全国網羅 |
|---|---|---|---|
| 事業所の基本情報 | [WAM NET 障害福祉サービス等情報公表システム オープンデータ](https://www.wam.go.jp/content/wamnet/pcpub/top/sfkopendata/) | 全国一括 | ✅ 47都道府県 |
| 工賃（賃金）実績 | 各都道府県が公表する工賃実績資料 | 都道府県ごと | ❌ 取り込み済みの県のみ |
| 生産活動 | 一部の都道府県の公表資料 | 都道府県ごと | ❌ 3都道県のみ |

**工賃と生産活動は、国が事業所別に一括公表していません。** 都道府県ごとに、様式も形式も
（Excel / PDF）も対象年度もバラバラの資料として出ています。そのため全国網羅はできず、
取り込み済みの都道府県だけにデータが付きます。画面上でも、どの県が対象かを明示しています。

### 更新は年2回しかない

元データは **3月末・9月末時点のスナップショットが年2回** 配布されるだけです。
リアルタイムな事業所情報は原理的に作れません。本アプリは
「公的スナップショットを、鮮度を明示した上で横断検索できるもの」です。
画面には常にデータ基準日を表示しています。

### 利用条件（公開前に必ず確認すること）

WAM 側はオープンデータの二次利用にあたり **利用状況の報告フォームへの記入** を求めています。
一般公開する前に現行の利用規約を確認し、報告手続きを済ませてください。
本リポジトリはこの手続きを代行しません。

## Phase 0：実データ調査の結果

設計は推測ではなく実データの確認にもとづいています。以下は確認済みの事実です。

### 配布形式

| 項目 | 実測値 |
|---|---|
| 形式 | ZIP（中に単一CSV）、**UTF-8 BOM付き** |
| 配布単位 | **サービス種別ごとの全国一括**（都道府県別ではない） |
| 列数 | 29列（全サービス種別で共通） |
| 利用可能な期 | 202111 / 202203 / 202209 / 202303 / 202309 / 202403 / 202409 / 202503 / 202509 / 202603 |
| 一覧ページの文字コード | CP932（ZIP内CSVとは異なる） |

ZIPのファイル番号（`sfkopendata_202603_045.zip` の `045`）は**サービス種別を表しますが、
ページ上のラベルとの対応が読み取りにくいため決め打ちしていません。**
最終判定は CSV 内の「サービス種別」列の値で行っています。

実測した対応：`045`=就労継続支援A型 / `046`=就労継続支援B型 / `060`=就労移行支援 / `062`=就労定着支援

### 件数（2026年3月末時点）

| サービス種別 | 件数 |
|---|---|
| 就労継続支援B型 | 20,783 |
| 就労継続支援A型 | 4,650 |
| 就労移行支援 | 3,396 |
| 就労定着支援 | 2,038 |
| **合計** | **30,867** |

### 取得できる項目・できない項目

**含まれる**（29列）：都道府県/市区町村コード、指定機関名、法人名・かな・法人番号・住所・電話・FAX・URL、
サービス種別、事業所名・かな・**事業所番号**、事業所住所・電話・FAX・URL、
**事業所緯度・経度**、利用可能時間帯（平日/土/日/祝）、定休日、特記事項、定員

**含まれない**：対象障害種別、指定年月日、開設年月日、休止・廃止フラグ、平均工賃・賃金、
加算の取得状況、送迎の有無

→ 緯度経度が最初から入っているため、**ジオコーディングの工程は不要**です。
→ 工賃実績は別の公表物（厚生労働省が年度ごとに公表）であり、本アプリの対象外です。

| 法人番号 | 約 6% |
| FAX | 約 9% |

## 精度をどこまで測ったか

「正確です」と言い切れる範囲を、実測できるものだけ数字にしています。

### 工賃・生産活動の突合精度（実測）

事業所番号を持つ資料（福岡・岡山・愛知）を正解データとし、番号を隠して
名称ベースで突合したときに同じ事業所を選べるかを測りました（`npm run audit`）。

| 指標 | 実測値 |
|---|---|
| 検証対象 | 2,211件（番号で確実に突合できた工賃レコード） |
| 名称だけで突合できた | 1,764件 |
| うち同一事業所を指していた | 1,763件 |
| **誤って別の事業所を指した** | **1件（0.06%）** |
| 適合率 | **99.94%** |
| 再現率 | 79.7% |

唯一の誤りは、岡山県の資料が「きずな」の市区町村を美作市と記載しているのに、
同じ行の事業所番号は勝央町の事業所を指している、という**資料側の不整合**です。

この数字は、事業所番号を持たない資料（北海道・千葉・大阪・神奈川・和歌山・新潟）の
確からしさの根拠として使えます。

### 測定の過程で見つけて直した不具合

| 見つけたもの | 影響 | 対応 |
|---|---|---|
| 長音符「ー」をハイフンに正規化していた | 「ラポール」と「ラポ-ル」が同一視され、別事業所を取り違える | 名称からは外し、住所（「１ー２ー３」表記が実在）にのみ残した |
| 市区町村が分かっているのに県全体へフォールバック | カナ正規化で同名になった別の市の事業所を掴む（実測で誤りの大半） | 市区町村の整合を必須にした |
| 郡の有無で市区町村照合が失敗（「大治町」と「海部郡大治町」） | 正しい事業所を弾いていた | 郡名を除いた形でも照合 |
| 圏域名・行政コードを市区町村として扱っていた | 和歌山93→56%、新潟96→35%に低下 | 実在する市区町村として解釈できるときだけ条件に使う |
| 平均工賃の検算式が1通りだけ | 正常な行を大量に誤除外 | A型・B型で分母が違うため、どちらかに合えば通す |

### 重複の実態

同名・同住所で複数レコードになるもの 215組（稼働27,452件の0.8%）を調べた結果：

- **202組**は同一建物の別サービス（例：コンフィデンス日本橋＝就労移行支援と就労定着支援が別指定）。分けて正しい
- **13組**（0.05%）が同名・同住所・同一サービスで、指定替えの疑い

## 設計上の判断

### 1. 事業所番号は一意ではない

「事業所番号」は事業所の主キーになりません。実データで確認したところ、
**同一の事業所番号で、名称も住所も異なる事業所が 1,288 件**ありました。

一方 `NO（システム内の固有の番号）+ サービス種別` は完全に一意（30,867件）です。

### 2. 施設の同一性キーに住所を含めない

住所には**建物名・階数・部屋番号**が含まれ、これらは頻繁に変わります
（例：`澄川８８ビル２階` → `澄川８８ビル３階`、`PP千歳ビル` → `アスクゲートビル`）。
住所をキーに含めると、同じ施設が期をまたぐたびに別レコードに分裂します。

候補キーを実データ（202509→202603）で比較した結果：

| キー | 誤って「消失」扱いになる数 | 別事業所を混ぜる過剰マージ |
|---|---|---|
| 事業所番号 + 名称 + 住所 | 959 | 0 |
| **事業所番号 + 名称** ← 採用 | **576** | **0** |
| 名称 + 市区町村 | 530 | 618 ← 不採用 |

過剰マージを起こさずに誤検出を最小化できる「事業所番号 + 正規化名称」を採用しました。
この判断は `test/normalize.test.mjs` にテストとして固定してあります。

### 3. 消えたレコードは削除しない

スナップショットに現れなくなった事業所は削除せず `presumed_closed` として残し、
最終確認期を記録します。UI では「最新データに掲載なし（〇年〇月が最後）」と表示します。

ただしこれは**廃止の確認ではありません**。事業所番号の変更・改称・移転でも同じ状態になります。
そのため、名称と市区町村が一致する現役レコードがある場合は
**名寄せ候補として詳細画面に提示し、自動では統合しません**（現在 718 件）。

### 4. 工賃は「計算式が合うか」で検証してから採り込む

PDFの表は行によって桁がずれることがあり、支払総額を平均額として読んでしまうと
「B型で月額1,300万円」のような値がそのまま入ってしまいます。

そこで、平均工賃が計算式と整合するかを毎回確かめています。
ただし計算式は方式によって分母が違うため、**どちらかに合えば通す**という判定にしています。

- 対象者延人数方式（A型・旧方式）: `平均 = 支払総額 ÷ 対象者延人数`
- 新計算方式（B型）: `平均 = 支払総額 ÷（1日の平均利用者数 × 年間開所月数）`

どちらにも合わない行は取り込みません。この検証を入れる前後で、
取り込んだ工賃の県平均は厚生労働省の公表値と整合するようになりました。

| 都道府県 | 取り込んだB型の平均工賃 |
|---|---|
| 北海道 2024年度 | 26,536円 |
| 千葉県 2024年度 | 22,110円 |
| 神奈川県 2023年度 | 20,219円 |
| 大阪府 2024年度 | 19,910円 |

（参考：厚生労働省が公表した令和5年度のB型全国平均は 23,053円）

### 5. 工賃・生産活動は「確実に結び付くもの」だけ紐付ける

都道府県の工賃資料の多くは事業所番号を持たず、事業所名と所在地で照合するしかありません。
次の順に照合し、**候補が複数残る場合は結び付けません**。
誤って別の事業所の工賃を表示するより、「該当なし」のほうが害が小さいためです。

1. 事業所番号
2. 法人番号 + 事業所名
3. 都道府県 + 市区町村 + 事業所名
4. 都道府県 + 事業所名
5. 都道府県 + 事業所名 + 法人名

突合方法は1件ずつ記録し、詳細画面に「この事業所との突合方法」として表示します。
事業所番号や法人番号を持つ資料（岡山・愛知・新潟）は97〜99%、
名称だけで照合する資料（北海道）は74〜80%が結び付きました。

### 6. 検索は FTS5 ではなく LIKE

FTS5 の trigram トークナイザは3文字未満のクエリに反応しないため、
「就労」「東京」といった2文字の日本語検索が機能しません。
正規化済みカラムへの `LIKE` は 3万件規模で **1.7〜20ms** で応答するため、こちらを採用しました。

検索文字列は全角/半角・大文字小文字・カタカナ/ひらがなを正規化して突き合わせます
（「スマイル」でも「すまいる」でも同じ 367 件がヒットします）。

### 7. SQLite を使う理由

元データが年2回更新の読み取り中心のデータであり、サーバ運用を必要としないためです。
PostgreSQL + PostGIS は運用コストに見合いません。

## スプレッドシートへの書き出し

`npm run export` で `data/export/` に出力します（アプリの「スプレッドシート用に全件を書き出す」からも取得可）。
BOM付きUTF-8のCSVなので、Excelはそのまま開けます。Googleスプレッドシートは「ファイル > インポート」。

| ファイル | 内容 | 行数 |
|---|---|---|
| `00_はじめに.csv` | 各シートの説明と、精度・注意点 | — |
| `01_事業所一覧.csv` | **1行=1事業所**。サービスごとの定員を列に展開済み。まずこれ | 32,147 |
| `02_サービス.csv` | 1行=1サービス。営業時間・定休日つき | 36,913 |
| `03_工賃.csv` | 1行=公表資料の1行。**未突合の行も残す** | 7,915 |
| `04_生産活動.csv` | 1行=公表資料の1項目 | 4,472 |
| `05_データソース.csv` | どの県のいつのデータをどこから取ったか | 17 |

どの行にも **出典URL・データ基準・突合方法** を入れてあります。表計算に移したあとでも、
その数字がどこから来たのかを辿れるようにするためです。

`03_工賃.csv` は突合できなかった行も「未突合」として残しています。
落としてしまうと、資料に載っているのに見えない行が出て、件数の突き合わせができなくなるためです。

## 構成

```
src/
  ingest/
    sources.mjs     データソース定義（新しいソースはここに1つ追加する）
    fetch.mjs       一覧ページを解析してZIPを発見・取得（URLはハードコードしない）
    unzip.mjs       依存なしのZIP読み取り
    csv.mjs         RFC4180準拠のCSVパーサ
    normalize.mjs   正規化（全角/半角・かな・住所分解・法人格除去）
  db/
    schema.sql      スキーマ
    build.mjs       raw → normalized → merged、スナップショット差分、名寄せ候補
  server.mjs        読み取り専用API + 静的配信
public/             検索UI（ビルド不要）
test/               正規化・同一性キーのユニットテスト
data/
  raw/<期>/         取得した生ZIP（再取得できないため保存する。gitignore対象）
  shuro.db          構築済みSQLite（gitignore対象）
```

### API

| エンドポイント | 内容 |
|---|---|
| `GET /api/meta` | データ基準日、サービス種別、都道府県、品質指標 |
| `GET /api/facilities` | 検索（`q` `pref` `city` `service` `capacity_min` `capacity_max` `status` `sort` `page` `per`） |
| `GET /api/facilities/:key` | 詳細（提供サービス、関連事業所、名寄せ候補、履歴） |
| `GET /api/cities?pref=` | 市区町村一覧 |
| `GET /api/places?q=` | 地名（都道府県＋市区町村）の候補。市区町村を全国から直接選ぶため |
| `GET /api/map` | 検索条件に合う全件の座標（上限3,000件）。地図がページ内20件に縛られないため |
| `GET /api/trend` | 期ごとの掲載件数と新規・消失 |
| `GET /api/export.csv` | 検索条件と同じパラメータでCSV出力（BOM付き） |

## 未実装・既知の制約

- **工賃・生産活動は全国網羅ではありません。** 国が事業所別に一括公表していないためで、
